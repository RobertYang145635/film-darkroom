## 2. 必须更正的事实错误（3 条，会误导下一个执行者）

### 2.1 研究笔记 §3.2 的坐标断言是错的，且与自家审计互相矛盾
`docs/research/2026-09-consistency-rescue.md` §3.2 写：

> "VIEW 场景坐标 == oriented small == `_positive_full` 坐标……零换算"

代码不成立。`_compose_view`（`main_window.py`）在**调整阶段且未勾选保留片边**时会切片：

```python
if out is not None and self.current_page() == 1 and not rec.keep_rebate:
    ...
    rendered = rendered[y0:y1, x0:x1]   # ← 显示图原点 = 整幅正片的 (x0, y0)
```

而 `_on_point_picked` 的注释正是那句错误断言，并直接 `self._positive_full[py, px]` 采样。
→ 同一天写的 v6.1 审计 F5 已经把它列为"重要问题"并在真机上复现了。
**研究笔记必须加更正段**（"仅当输出裁切为整幅/勾选保留片边时成立"），
否则下一轮会照着它继续认为坐标链路无需处理。

### 2.2 CN400 离群帧的「偏离中位」数字与提交数据不符（含我本人的抄错更正）

**本节原文有错，2026-09-08 更正。** 研究笔记实际写的是
「CN400-12（-0.7315，偏离中位 +0.036 decade ≈ 8.7%）」——端点 −0.7315 是**对的**。
我上一条审查写成「文档说 −0.771 vs 中位 −0.809」，那是**我自己的抄错**，
不应记在被审对象账上；留在这里是为了让账目对得上。

仍然成立的问题只有一处，比原来说的小：按提交数据 9 帧实测，
中位 = **−0.7943**，CN400-12 偏离 = **+0.0628 decade ≈ 15.6%**，
而笔记写 +0.036 / 8.7%。极差 0.0838 与 max_abs_drift 一致，结论方向不变。
已在研究笔记原地更正（复算脚本口径：base_chroma.per_frame 第 3 列取中位数）。

教训依然有效，而且更贵了：**「结论对、数字错」会被下一份文档顺手抄走**——
这次连严格审查都抄错了一次。

### 2.3 度量输出目录里有脏文件与非法 JSON
- `outputs/research/roll_consistency/翻拍.json`：与 `1299_G200.json` 数字完全相同
  （n=11 / 30.0 / 46.6 / 10），但 `roll_dir=None`、`base_chroma={}`。
  说明**卷键控曾经把叶目录"翻拍"当成卷名**（三份有效输出的 `roll_dir` 都以 `\翻拍` 结尾，
  这个风险没消除），且证据目录留了一份与文档表格不一致的脏文件。
- 四个 JSON 都含裸 `NaN`（Python `allow_nan=True` 产物）→ **不是合法 JSON**，
  任何严格解析器（含前端）会直接抛错。请 `json.dump(..., allow_nan=False)`
  并在写前把 NaN 换成 null + 记 `invalid_count`。
- `outliers` 是字符串下标数组（`"0","1","3"`），没有帧名 → 人读不出是哪个洞。

## 3. 审计没列出、我新发现的问题（按影响排序）

### 3.1 全量测试在我的第一次运行中**硬崩溃**（flake，不是失败）
```text
第 81% 处：Windows fatal exception: access violation
  theme.py:191 apply
  tests/unit/test_v6_keep_rebate.py:35  qapp fixture
```
第二次运行同命令 → `355 passed in 124.42s`。单跑 `test_v6_keep_rebate.py` 也通过（7 passed），
`test_v6_pick_rescue_ui.py + test_v6_keep_rebate.py` 同进程亦通过（17 passed）。
→ 这是**多 QApplication / QSS 在全序列下的非确定性崩溃**，与测试逻辑无关，
但它意味着"355 全绿"不是可保证的 CI 事实。
建议：GUI 测试加 `-p no:cacheprovider --forked`（或每文件独立进程），
并把"连续 3 次全绿"作为绿灯定义，而不是跑一次。

### 3.2 从调整阶段切回分析阶段时，**拾点态没有被清除**（新缺陷，建议记为 F9）
- `preview_view.set_draw_mode(None)` 只在 `kind is not None` 时才清 `_pick_mode`；
- `_set_stage(0)` 只调 `set_draw_mode(None)` + 显示负片，**不清 pick**；
- `_on_point_picked` 也不检查 `self._stage`。

后果：用户在调整阶段点亮"中性点救援"，再点回"分析"看负片，此时画布仍是十字光标，
点下去会**用正片像素求解、并把结果显示在正片缓存里**——用户看着负片做"去色罩"。
v6.2 §7.6 已经写了要求（"分析阶段禁止中性正片拾点；切回阶段时退出拾点"），
但它不在 F1–F8 清单里、`§9.3` 回归矩阵也没有对应行 → **实现时大概率被漏掉**。
建议正式列为 F9 并进回归矩阵（断言：阶段 1 开拾点 → 切阶段 0 → `view._pick_mode is None`
且点击不产生 intent）。

### 3.3 开启拾点会**静默跳阶段**
`_on_pick_neutral(True)` 里 `if on and self._stage != 1: self._set_stage(1)`。
用户点一个按钮就被从"分析"扔到"调整"（ROI 叠加同时消失），没有任何提示。
小事，但正是社区抱怨的"我不知道自己在哪一步"（NLP 用户同类抱怨最多）。

### 3.4 (temp,tint) 控件刻度与感知强度严重不匹配（影响救援手感）
`rescue_demo` 实测：中和 **10% 蓝偏**需要 `d_temp=+74.6, d_tint=−74.8`；
暖偏需要 `+48.6 / −58.2`。也就是控件范围（±100）里，
**一次合理救援就要吃掉大半刻度**，之后用户几乎没法用滑杆做"再暖一点点"的微调。
建议：先给控件做刻度标定（每 1 单位 ≈ 多少倍增益 / 多少 ΔE），
必要时改成"感知均匀"刻度或把救援结果显示为增益倍数而不是控件值。

### 3.5 救援的"残差"是**自证度量**，文档表述过头
求解目标就是让被拾取 patch 的通道极差最小，然后又在同一个 patch 上量"极差从 0.494→0.001"——
**这个数必然变小**，它只能证明"求解器到达了二参数族内的最优"，
不能证明"这张图的颜色变好了"。现有测试同样只断言 patch 中位差缩小
（`test_rescue.py:109/146/161`），从未与任何参考成品比较。
两种诚实写法任选其一：
1. 把结论降级为"求解正确性证明"（并删掉"完全中和"这类视觉承诺）；
2. 加一个真正的端到端断言：注入已知色偏 → 救援 → **整幅图**与"注入前"的
   Lab ΔE 分布（p50/p95）显著优于不救援。第 2 项很便宜，我强烈建议做，
   因为它顺带回答"救援有没有副作用（把中性以外的区域带歪）"。

### 3.6 现在的"卷内一致性指标"量的不是我们输出的稳定性
提交数据里每帧只有：`base_source / base_dmin_used / candidate_default /
scene_confidence / neutral_frac / median_ab / shape / sec_per_frame`。
- `base_chroma`（场景无关，好）= **输入片基**的一致性 → 量的是胶片和冲洗，不是软件；
- `median_ab` = 输出色度，但被场景内容主导（文档自己已证明全图 ΔE 不可用）。
- **缺的正是**：每帧实际被施加的量（卷级增益 / 该帧 temp,tint / 与卷中位的偏离）。
现在这些信息在 `roll_analysis` 内部算过（`roll_gain_of`），但没有落进 JSON。
不补这一项，"把卷内一致性变成可观察的功能"这句话在数据层面还是空的。
（附带：`test_consistency.py` 18 项都是合成图，度量本身没错，但**没有一项**跑在真实样片上。）

### 3.7 联系表显示多帧方向与 NLP 参考不一致，而仓库没有方向来源证据
我直接看了 `outputs/quality/v5-p0-acceptance/rolls/1298_G200/contact-sheet.jpg`（Sep 2）：
中间四栏（preserve/neutral/warm/preserve）与"NLP 参考结果"之间，
**多帧呈 180°（部分行像 90°）差异**，且整体明显青蓝、低反差；
部分帧的片边/齿孔被包进输出（可见洋红/紫色边条）。
但仓库里没有任何证据判断差异来源：EXIF 方向？LibRaw `user_flip=-1` 的元数据方向？
还是用户在 LR 里手动转过？我试着读元数据也没读通（此 rawpy 构建不暴露 `other.flip`，
NEF 头部也没有可直读的 EXIF 标记）。

这件事必须查清，因为**方向的 180°/90° 会交换上下片基条带**，
直接污染"未曝光片基取样区"这一整条假设链。
最小实验（约 20 分钟）：对 12 帧解码后图像用"天空在上/地在上"的先验或
人工标 12 帧真实方向，与 `FrameRecord.rotation_degrees` 对齐统计；
顺带把"整卷同向 / 以这帧为正翻转全卷"做成一键（社区 t9885 Auto rotate request 就是这个）。

### 3.8 最重要的前置条件仍然没人动，而且已经不是模板问题了
五个卷的 `decisions.json` 我逐个数过值：**除 id 之外全是空字符串**，
从 9-02 到今天一个判定都没填。研究笔记 §5.1 也承认"仍缺：人眼判定基准集"。
现在救援、裁切 IoU 0.978、一致性锚点、三候选都有了实现，
**唯一缺的就是你手上的 40–60 帧判定**——它现在是全部结论的共同分母。

## 5. 对 v6.2 规格本身的两处收紧建议

1. **§6.6 "分析正在更新时阻止该帧导出"需要边界定义。**
   现在这句话按字面会波及 CLI/整卷自动导出（v5 承诺"自动检测不阻断普通导出"）。
   应限定为：**仅该帧、仅当用户已手工改动且分析未完成**时阻止；
   未手工改动的帧继续走自动路径，否则会把批处理重新变成需要逐帧点确认。
2. **§5.2 的冲突回退依赖"确认内容指纹 + 工作修订号"，但现有 JSON 里没有这两个字段。**
   规格应显式写明：draft/annotation schema 需要一次 bump（v4→v5），
   并规定**旧文件（无指纹/无修订）时的确定行为**（当前只写"不得声称逐字段恢复历史"，
   不足以让实现者决策）。不补这条，实现时会在"无法证明来源"处卡住或被随意发挥。
