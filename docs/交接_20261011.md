## 1bis 第二轮改动：`red_ratio 1.0 → 1.30`、`LOOK_CHROMA_GAIN 1.897 → 2.50`

外部依据：逐通道斜率是**片种表**——RawTherapee `filmnegative` 默认 `redRatio=1.36`、
FreeCCR `S[c]=1/log10(base[c]/dense[c])`、abpy 两块灰 patch 解三条斜率，
**没有一家把红斜率留在 1.0**。我们内部依据：11 帧中间带 `R−G` 我方恒为负（一律偏绿）。

上一轮"red_ratio 无效"的结论**作废**，两处污染：只看了蓝黄轴 `Δb` 与饱和（误差在 R−G 轴上）、
以及当时若干帧片基错 0.19~0.36 decade（片基直接进 `d=−log10(t/base)`，等于搬走自变量再测斜率）。

**两个旋钮各管一条轴**（这条是负控制逼出来的，不是我推出来的）：色相归斜率，
增益负责付斜率欠下的饱和账；只动增益反而把偏绿放大（留出 0.0377→0.0993）。
数字、锁、以及"我第一版把话写过头被锁抓到"的过程都在 `docs/blockers.md` B-14⑨。

**蓝指数 0.70 在 red=1.30 下重 check 过，结论是不动**（`tmp_blue_resweep.py`）：
标定卷 `1298`（8 帧）上 blue **0.55 更好**（中间带向量差中位 0.0366 对 0.0425），
但留出卷 `1299`（3 帧）上 0.55 更差（0.0276 对 0.0180），而 0.85 在标定卷最差（0.0571）。

## 2 本轮新否掉的路（不要再走）

1. **逐通道灰平衡（把平均密度拉成中性）**——他 11 张成品的 `APD(R−G)` 极差 **0.691**、
   `B−G` **0.784** decade，跟着场景走（`::G200-9` 的 `B−G=+0.740` 是一片天）。
   工业界能做是因为**只靠拢 20%、限幅 ±0.12**（NegPy），不是拉平。
2. **LATD 闭环（用卷中位反推片基）**——片基正确的 11 帧，R/G 偏差中位只 0.033，
   但 **B 最大 1.738 decade**，全是场景（蓝天）。拿它当目标会把内容当误差修掉。
3. **Dmax 改成与打印锚点同区（中心 70%）**——空操作：`1299` 三帧 Dmax
   1.331/1.304/1.254 → 1.348/1.329/1.246，四统计距离 0.0679→0.0680。
4. **顺带把上一轮自己的怀疑也了结**：曾怀疑"Dmax 扫过没效是因为扫描区间太窄（只 ×0.8~1.25）"。
   本轮按机制重新推了一遍并实测：**不是区间问题，这条确实无效**。
   中心区亮度只占 [0.50,0.63] 是内容/翻拍本身，不是 Dmax 造成的。

## 3 外部机制对照的结论（本轮最大的一块新知识）

- **锚点是物理的**：硬件量片基一律在**只含胶片的窗口**上取 **99.9 分位**
  （Coolscan 逐通道计量到 99.9、落在满量程 97%；Pakon 取数例程阈值 `thr=n/1000`）。
  我上线的 99.9 分位与两处独立出处同值。
- **曲线是固定的，只有电平（和反差档）跟帧走**，而且**部分靠拢 + 限幅**
  （NegPy `anchor = assumed + 0.2·(m − assumed)`，限幅 ±0.12；grade 是 ISO-R 50–180 的档位）。
- **没有一个可信实现用内容分位数定输出黑白点**，也**没有一个用全局色度增益**
  （色度来自逐通道斜率或密度域矩阵）。我们的 `P_LOW/P_MID/P_HIGH` 与
  `LOOK_CHROMA_GAIN=1.897` 在这两点上都是少数派。
- **darktable `negadoctor` 的 `D_max` 是手动的**，注释理由："任何由内容推出来的最大值都是场景相关的"。
  这条直接质疑我们的 p95 白锚。
- **"UCA" 这个词查无出处**（专利/说明书/论坛都没有）。能证实的只有"激进边缘增强会留下彩色描边"。
  以后引用它之前先找到源。
- 卷级积分是**专利化的策略**（US5223892A：整卷平均密度→一个曝光印所有帧），
  不是工程师习惯；操作员侧有 [Hold] 键与 ±3 密度键 / C-M-Y 键。
  全部出处见 `docs/blockers.md` B-14①。

## 8 第四轮（同日最晚）：高光残留色罩——⑲ 是一次**自我推翻**

用户说"继续"之后做的事。⑰ 判否"高脱色"用的尺子（`|Δp95|` 显示亮度 + 四统计距离）
**对它声称要修的缺陷不敏感**：分层一量就露馅——技术正片的最高 5% 像素彩度只有
0.122~0.128（接近中性），成品被打印层的 `k=2.50` 推到 0.226~0.249，
而用户参考是 **0.006~0.031**。也就是"水是一片死青"是**我们自己造出来的**，
不是反相带出来的。⇒ 上线 `k_eff` 在纸级末端 15% 从 2.50 线性收到 **0.80**
（`print_math.chroma_gain_at`，亮度不参与，所以不推翻 ⑮ 的电平）。

- **实测**（`tests/regression/test_highlight_desaturation.py -s`）：
  高光最低通道差 `0.1632 → 0.1163`（留出卷 `0.2935 → 0.2172`）、
  高光彩度差 `0.1259 → 0.0773`、白点缺口 `Δp95 −0.0463 → −0.0188`；
  **反向放大**（`k_hi=4.2`）`0.1944` 比关掉更差 ⇒ 方向承重；
  `1298::G200-9` 的最低通道 0.734 → **0.840**，与他**逐位对上**。
- **代价写进锁当预算**：训练卷四统计距离 0.0586 → 0.0604（预算 0.006）、
  Δsat95 −0.0204 → −0.0278（预算 0.015）。**裁决靠看图**
  （`highlight_desat_3way.jpg` 三列）：涨的那两项来源都不是这条机制要修的缺陷。
- **一帧不同意**：`1298::G200-5` 他的高光本来就带暖彩度（0.151），
  我们上线后从 0.782 走到 0.840，离他更远 +0.058。这是"全局一条斜坡"的固有代价；
  要逐帧分辨得靠 ⑩/⑪ 的空间片基场。
- **本轮又抓到两个自己的错**（都留在账上）：
  ① 斜坡起点第一版当**显示亮度**扫，`t0=0.88` 时**一个像素都没进斜坡**
  （三档 `k_hi` 逐比特相同）才发现 `_remap_band` 的 `y` 是线性纸级、上限 0.80375；
  ② 回归锁里 `p_up/p_off` 两个变量名写反，使"白点朝参考走"那条断言**方向反着也能过**，
  跑出来才抓到 ⇒ 现在这类对照一律用 `ship_ / inert_` 全名。
  另外 `chroma_gain_at` 里原先有个"基增益 ≤ 高光档就恒等"的保护，
  它会让反向负控制**空转**（`k_hi=4.2` 与 2.5 逐比特相同），已去掉并写明不许加回。
- **教训（已写进记忆 `repo-delivery-invariants` 第 4 条）**：
  "换了四种独立改法某个缺口都不动"是**指标选错**的信号，不是"此路不通"的证据；
  **判否一个机制之前，必须先造一把对它敏感的尺**。
